## Befunde zur Implementierung

### FW26-01 — P1 — Waage 3 und 4 gehen mit Funkformat v2 verloren

- **Fundstellen:** `firmware/STM32_LORA_261008_ZS/Config_MULTI.h` (`Anzahl_Sensoren_Gewicht`: 1–4), `STM32_LORA_v2.ino` (`prep_payload_v2`), `funkformat_v2.h`.
- **Ist:** V2 überträgt ausschließlich `Gewicht[0]` und `Gewicht[1]`. V2-Spezifikation kennt keine Gewichte 3/4.
- **Risiko:** Bei drei oder vier konfigurierten Waagen fehlen Werte unbemerkt.
- **Abhilfe / Akzeptanz:** Entweder V2-Protokoll samt Formatter/Server erweitern **oder** bei `FUNKFORMAT == 2 && Anzahl_Sensoren_Gewicht > 2` einen Compile-Time-Fehler ausgeben.
- **Status:** Per Code nachgewiesen; nicht gefixt.

### FW26-02 — P1 — Unkalibrierte Waage erzeugt scheinbar gültiges Gewicht

- **Fundstellen:** `Config_MULTI.h` (Standard-`Taragewicht[0] == 10`); Haupt-Sketch (Gewicht-Initialisierung `0.01f`); `beelogger_HX711_STM.ino` (`Sensor_Gewicht`); `STM32_LORA_v2.ino`.
- **Ist:** `Sensor_Gewicht` überspringt bei Platzhalterkalibrierung die Messung, aber `Gewicht[0]` bleibt `0.01f`. Der V2-Packer wertet jeden Wert ungleich `No_Value (-1)` als gültig.
- **Risiko:** 0,01 kg wird als reale Messung übertragen.
- **Abhilfe / Akzeptanz:** Gewicht auf einen eindeutigen Ungültigzustand initialisieren; erst nach erfolgreicher Messung gültig setzen; V2-Fehlerbit setzen bzw. bei fehlender Kalibrierung Kompilierung sperren. Auch beim HX711-Timeout prüfen.
- **Status:** Per Code nachgewiesen; nicht gefixt.

### FW26-03 — P1 — Unbegrenztes ADC-Polling

- **Fundstelle:** `STM32_LORA_v2.ino`, `v2_adc_lesen`.
- **Ist:** `while (!(ADC1->SR & ADC_SR_EOC)) {}` ohne Obergrenze.
- **Risiko:** Bei blockiertem ADC bleibt der autarke Logger wach und erreicht den regulären Schlafpfad nicht.
- **Abhilfe / Akzeptanz:** Zeit-/Zyklenlimit, Fehlerausgang, ADC abschalten, Messung ungültig und geordneter Rückweg zu `System_ShutDown`; optional unabhängiger Watchdog.
- **Status:** Per Code nachgewiesener unbegrenzter Wartepfad; tatsächlicher Hardwarefehler nicht nachgewiesen.

### FW26-04 — P1 — Neue Hosttests / Buildvarianten fehlen in CI

- **Fundstellen:** `.github/workflows/tests.yml`, `tests/alle_tests_linux.sh`, `tests/firmware/`.
- **Ist:** Grüner Standard-Build mit `beelogger_Audio = 0`, aber kein verpflichtender Audio-Build und keine Ausführung der zwei neuen Hosttests in Actions.
- **Abhilfe / Akzeptanz:** GitHub Actions führt FFT-Test, C-vs-JS-Vektoren und mindestens die Kombinationen V2/Audio EIN + V2/Audio AUS + V1/Audio AUS aus. Nach dem ersten erfolgreichen Audio-Build Warnungen und Speicherverbrauch auswerten.
- **Status:** CI-Konfiguration geprüft; Lücke bestätigt.

### FW26-05 — P2 — 50/59 Hz und Rauschen können FFT-Ergebnisse beeinflussen

- **Fundstelle:** `bee_fft.h`: `BF_F_MIN=60`, Peakinterpolation, `e.gueltig` schon bei `leistung[kp] > 0`.
- **Ist:** Das Auswertefenster ist kein analoger Hochpass; Peaks unterhalb 60 Hz können durch Interpolation gemeldet werden. Rauschen kann eine „gültige“ Peakfrequenz liefern.
- **Abhilfe / Akzeptanz:** Produktkriterium für Spitzen-Gültigkeit (Mindestpegel/SNR); interpolierte Peakfrequenz auf den vorgesehenen Nutzbereich begrenzen, sofern das fachlich gewünscht ist; gezielte Tests mit 50, 55, 59, 60, 61 Hz sowie Rauschen/Clipping.
- **Status:** Rechnerische Spotchecks; tatsächliche Mikrofon-Eingangsdynamik ungeprüft.

### FW26-06 — P2 — Audioaufnahme trotz FPort 1

- **Fundstellen:** Hauptsketch `loop` ruft `Sensor_FFT()` immer auf; `STM32_LORA.ino` sendet bei `FUNKFORMAT=1` ausschließlich Legacy-Payload.
- **Risiko:** Bei Audio EIN + Legacy-Payload unnötige Aktivzeit und Energieverbrauch.
- **Abhilfe / Akzeptanz:** Audioaufnahme nur bei V2 aktivieren oder ein bewusstes Diagnostik-Feature daraus machen.
- **Status:** Per Code nachgewiesen.

### FW26-07 — P2 — Prototypen-Abtastung weicht vom Hardware-Lastenheft ab

- **Fundstellen:** `hardware/LASTENHEFT.md` (ADC-Trigger per Timer/DMA), `STM32_LORA_v2.ino` (DWT-Zyklen + gepollte ADC-Wandlung).
- **Einordnung:** DWT-/Polling-Verfahren kann auf dem Musterlogger ausreichend sein; es erfüllt jedoch **nicht** den dokumentierten DMA-Entwurf der späteren eigenen Platine.
- **Akzeptanz:** Abtastjitter, Anzahl überfälliger Abtastungen und Energiebedarf am Gerät messen; Prototyp und Zielarchitektur getrennt dokumentieren.
- **Status:** Architekturdifferenz bestätigt; keine Aussage über tatsächliche Genauigkeit ohne HiL.

## HiL-Plan / Akzeptanzkriterien

1. Konkretes BlackPill-Binary mit Audio EIN erfolgreich bauen; Flash, SRAM, Stackreserve protokollieren.
2. Kaltstart, reguläres RTC-Wakeup, Reset-Grund (RCC-/PWR-Flags) und Shutdown per UART prüfen.
3. ADC-/DWT-Abtastung über 9.342 Werte bei unterschiedlicher CPU-Last; Überlaufzähler und Zeitdauer messen.
4. Sinus-/Mischsignale 50, 55, 59, 60, 61, 180, 247,3, 500, 700, 900, 1.100 und >4.096 Hz; Amplitude, Offset, Clipping und Rauschen dokumentieren.
5. Sensoren einzeln entfernen und wieder anschließen: kein Ersatzwert, korrektes Zustandsbit, kein Phantomgewicht.
6. V2-Rohbytes → TTN-Formatter → `server/lora/lora_eingang.php` → `week.csv` / `lora_zusatz.csv` vergleichen.
7. Gerätzeit/DeviceTimeReq bei RX1/RX2 sowie Nichtantworten; Standby/Weckraster und Stromaufnahme messen.
8. 24-h-Dauerlauf am Tisch, danach erst kontrollierter Feldeinsatz.
